# DeepSeek chat-demo 本地化改造说明

本目录是 DeepSeek 官方 `chat-demo v0.1.2` 的**构建产物**，在其之上做了一层旁路改造，
新增以下能力：

1. **对话自动存到本地文件夹**（如 `E:\chat`），不受清理浏览器数据影响，可跨浏览器通用
2. **可配置多个模型提供方**（官方 / 中转站 / 自建服务），每个提供方各自一个 API Key
3. **可选模型**：设置里可「获取模型」并**多选**要保留的模型，输入框旁也有快捷切换器
4. **API Key 可存到同一文件夹**，换浏览器或清缓存后自动恢复
5. **各种设置也存到文件夹**（语言、主题、思考/联网开关、提供方与模型选择等）
6. **每条回答显示真实模型名**（读取接口返回的真实值，而非界面写死的标签）
7. **界面切换动效**：弹窗、侧栏、对话切换、消息列表都有淡入与滑动过渡；侧栏展开/收起平滑收放；模型上拉栏向上展开、向下收起；跟随系统「减弱动态效果」设置，也可在设置里一键关闭

---

## 一、怎么用

### 启动（必须先起本地服务，不能双击打开）

```powershell
cd chat-demo-v0.1.2
node tools/serve.mjs
```

然后浏览器打开 **http://127.0.0.1:8080**

> ### ⚠️ 为什么不能直接双击 index.html
>
> 两个硬性限制：
> 1. **文件夹读写权限**（File System Access API）只在**安全上下文**下可用。
>    `file://` 协议不算安全上下文，`http://localhost` 和 `https://` 才算。
> 2. 页面用了 ES module 与跨文件加载，`file://` 下会被浏览器的同源策略拦掉。
>
> 所以本地测试请一律用上面的 `serve.mjs`；上线走 HTTPS（GitHub Pages 自带 HTTPS，没问题）。

### 首次设置

打开页面 → 点右上角设置 → 找到 **「本地文件夹存储」** 区块：

1. 点 **「选择文件夹…」** → 选一个目录（例如 `E:\chat`，建议新建专用目录）
   - 浏览器会弹窗问「允许本站修改此文件夹中的文件？」，点**允许**
   - 只需要点这一次；之后每次打开页面若浏览器要求确认，点一下「重新连接」即可
2. 连接成功后会自动把现有对话写进该文件夹
3. 想连 API Key 一起保存，点 **「保存到文件夹」**（**请先读下面的安全警告**）

> **关于「输入 API Key 开始使用」**：官方应用首次打开会停在引导界面，
> 要求你输入 Key 并点「确定」校验一次。这一步是**官方自身逻辑**，
> 校验请求会发往你当前配置的 API 地址（`GET {地址}/models`）。

> ### 官方那个统一 Key 输入框 vs 自定义提供方
>
> 官方自带一个 Key 输入框，位置在 **设置 → 数据管理 → 最上面那一行**
> （未填时显示「输入 API Key 开始使用」，填过之后显示掩码和铅笔图标）。
> 它代表**官方那一路**（也就是应用自带的统一配置）。
>
> 为了避免「同一个 Key 有两处可改」的困惑，**模型提供方区块不再列出官方**，
> 只列你自己添加的提供方：
>
> - 想改官方那一路的 Key → 用**数据管理**里的那个输入框
> - 想改官方那一路的地址 → 用**通用设置**里的「自定义 API 地址」
> - 想用中转站等其它端点 → 在**通用设置 → 模型提供方**里添加
>
> 桥接层会持续对账：在官方面板里改 Key 会同步进当前提供方，
> 且**只在官方那一路生效时**才这么做 —— 免得把自定义提供方各自的 Key 覆盖掉。

### 日常使用

- 每次对话**自动保存**到文件夹，无需手动操作
- **换浏览器 / 清空缓存后**：打开页面 → 连接同一个文件夹 → 完成
  - **设置会自动带回**（语言、主题、提供方与模型等，来自 `数据/settings.json`）
  - **对话也会自动读回**（仅当本机是空的、且从没同步过，才会自动做，避免误覆盖）
  - 如果自动恢复没触发（例如本机已经有数据），可以手动点
    **「从文件夹恢复设置」** / **「从文件夹恢复」**
- 浏览器安全模型决定了：**每个浏览器都要单独"选择文件夹"授权一次**
  （句柄和权限是浏览器各自的，无法跨浏览器共享）。
  这一步必须在页面上点按钮完成，无法自动化 —— 但只需做一次。

> #### 为什么换浏览器后必须重新选一次文件夹？
>
> 文件夹句柄由浏览器的 File System Access API 保存在该浏览器自己的存储里，
> 并且重新获得读写权限需要**用户手势**（一次点击）。
> 这是浏览器的安全限制，不是本改造的缺陷。
> 连接之后，设置与对话都会自动同步，不需要再手动搬运。

### 配置模型提供方

**官方那一路不再作为卡片列出。** 它由应用自带的统一配置负责：

- API 地址：设置 → 通用设置 → **「自定义 API 地址」**
- API Key：设置 → **「数据管理」** → 最上面那一行（应用自带）

设置 → 通用设置 → **「模型提供方」** 区块里**只列你自己添加的提供方**：

1. 每个提供方可以填 **名称 / API 地址 / API Key**，各自独立
2. 点 **「获取模型」** 会去该地址拉取模型列表
3. 拉回来的列表是**多选**的：**勾选**你要保留的模型，再选一个「默认模型」
   - 「全选 / 取消全选」可一次性操作
   - 接口没返回的模型可以用下面的输入框**手动添加**（每行一个）
4. 点 **「保存」** 生效
5. 点 **「设为默认」** 切换当前使用的提供方
6. 区块顶部会显示**当前生效**的是官方统一配置还是某个自定义提供方；
   切到自定义后会出现 **「切回官方统一配置」** 按钮

> 这样做是为了避免「同一个 Key 有两处可改」的困惑：官方一个输入框，
> 自定义提供方各自一个，互不干扰。

> ⚠️ **本应用只讲 Anthropic 协议**（`POST {地址}/anthropic/v1/messages`）。
> 所以这里的「多个提供方」指的是**多个 Anthropic 兼容端点**。
> 纯 OpenAI 协议（`/v1/chat/completions`）的服务**无法直接使用**，
> 除非该服务端额外提供 Anthropic 兼容端点。

### 切换模型

输入框右上角有一个模型切换器（显示当前模型与提供方）：

- 点它可以直接切换模型，**不需要刷新页面**
- 菜单里也能切换提供方，**同样不需要刷新页面**，并且会留在当前对话
  （bundle 补丁让 API Key 与模型都是「每次请求时现读」，见技术说明第 13 条）

## 二、文件夹里会有什么

```
E:\chat\
├── README.md                    ← 自动生成的说明，日后自己看得懂
├── 对话\
│   ├── 20260214-143022_帮我写个正则.md      ← 人类可读全文（可直接阅读/搜索）
│   └── 20260214-143022_帮我写个正则.json    ← 结构化原始数据（含所有分支版本）
├── 附件\
│   └── <fileId>.<扩展名>                   ← 上传附件的**原件**（图片、PDF、Word、代码…都存）
└── 数据\
    ├── sessions.json            ← 全部对话索引
    ├── files.json               ← 附件清单（含 storedAs 指向 附件/ 里的文件名）
    ├── manifest.json            ← 存档元信息（含上次同步时间）
    ├── settings.json            ← 界面偏好（**不含密钥**，可安全阅读）
    └── apikey.json              ← 仅当你启用「API Key 存到文件夹」时才存在
```

**文件名规则**：`日期-时间_对话标题`，时间取该对话**最后更新时间**。
改了标题或产生新消息，文件名会跟着变，旧文件自动清理。

**双向自动同步**：这个文件夹是**实时**双向的，不需要手动点任何按钮。

| 方向 | 触发时机 | 行为 |
| --- | --- | --- |
| 应用 → 文件夹 | 你发消息 / 收回复 / 新建 / 改名 / 删除 | 防抖 700ms 后整目录快照落盘 |
| 文件夹 → 应用 | 每 3 秒扫一次（闲置降到 20 秒；标签页切回来立刻补一次） | 发现比本地新的对话就自动收进来并刷新页面 |

所以你在**网页版**（或另一台机器、另一个浏览器）新建的对话，只要那个浏览器
也连着同一个文件夹，本机这边几秒内就会自动出现 —— 不用再去点「从文件夹恢复」。
「从文件夹恢复」现在只在**首次连接**或**想强制覆盖**时才需要用。

判定「哪些文件是外部改过的」用的是三级判据，见 `pollFolderForChanges()`：
先用 `文件名|大小|修改时间` 粗筛（没变的文件连读都不读），再比内容哈希
（避免整目录重写被误判成新对话），最后比会话自己的 `updatedAt`
（避免把本地更新的内容用旧文件盖回去）。

如果不想让它自动收，把 `chat-demo:local-watch` 设成 `'false'` 即可。

**附件落盘**：所有类型的附件原件都会写进 `附件/`，文件名是 `<附件id><扩展名>`
（扩展名优先取原文件名，没有就从 MIME 猜）。`数据/files.json` 里每条记录都有
`storedAs` 字段指回那个文件；若某条记录**没有** `storedAs`，说明浏览器索引库里
本来就没存原件（早期版本或对方接口未返回），不会伪造文件。
反过来，`附件/` 里的原件在「从文件夹恢复」时也会被读回浏览器索引库。

**Markdown 里有什么**：每一轮对话一个 `##` 标题，助手消息后面会标注真实模型名，例如
`## DeepSeek  ·  2026-02-14 14:30:22  ·  \`deepseek-v4-pro\``；深度思考内容折叠在
`<details>` 里；附件以列表形式列出。

**关于分支**：这个应用支持「编辑消息后重新生成」，会产生多个回答版本。
- `.md` 里只有你**当前选中**的那条路径（你看到什么，文件里就是什么）
- `.json` 里保留**全部分支**，用于无损还原，不会丢历史版本

## 三、安全警告

### API Key 明文存储

启用「API Key 保存到文件夹」后，密钥以**明文**写在 `数据/apikey.json`。

- ✅ 好处：清空浏览器数据、换浏览器后自动恢复，不用重新输入
- ❌ 风险：**任何能读到该文件夹的人或程序都能拿到你的密钥**

因此：

- **不要**把这个文件夹放进网盘同步目录（OneDrive / 坚果云等）
- **不要**提交到 Git 仓库、不要打包发人
- 如果不放心：**不要**点「保存到文件夹」，密钥就只留在浏览器里（和官方原版行为一致）

想撤销：设置里点「删除文件夹中的密钥」。

### 对话内容

对话文件同样是你与模型的完整聊天记录，分享文件夹前请自行确认内容是否敏感。

### 设置文件不含密钥

`数据/settings.json` 是**纯偏好文件**（语言、主题、提供方列表与模型选择等），
**不包含任何密钥**，可以放心阅读和分享。密钥只在 `数据/apikey.json` 里。

## 四、改了什么（技术细节）

设计原则：**尽量不动官方压缩代码**，主逻辑走旁路层。

| 文件 | 改动 |
| --- | --- |
| `static/js/main.6fd9c886.js` | **4 处替换**：API 根地址改为读 `localStorage`；默认模型改为调用取值器（1 处定义 + 3 处调用点） |
| `index.html` | 注入一行 `<script src="localstore-bridge.js">`；标题改为「DeepSeek - 探索未至之境」 |
| `localstore-bridge.js` | **新增**，全部业务逻辑（约 6800 行，含注释） |
| `localstore-motion.css` | **新增**，界面动效层（可被设置里的开关关掉） |
| `localstore-brand.css` | **新增**，品牌外观层（logo / 应用名 / 一只鲸鱼图标 / 开屏标语），**不受动效开关控制** |
| `localstore-features.css` / `.js` | **新增**，功能扩展层（7 项功能，见第 27 条） |
| `images/logo.svg`、`images/whale.svg` | 界面上用到的两个图标 |
| `*.orig` | 官方原始文件备份，回滚用 |

技术要点：

1. **IndexedDB hook** —— 包裹原生 `IDBObjectStore.prototype` 的 `put/add/delete/clear`，
   感知官方写入后触发防抖（700ms）全量快照。不依赖任何压缩变量名，天然抗版本变化。
2. **全量重写而非增量** —— 每次快照读全部会话重写。
   改写标题 / 删除对话 / 切换分支等情况天然正确，无需复杂的增量对账。
3. **消息级自动同步** —— 除了 IndexedDB hook，还监听消息列表的 DOM 变化：
   流式回复过程中「内容还在追加但尚未落库」的窗口也能及时存盘，**不需要刷新页面**。
   为避免自注入节点（模型徽标、切换器）触发回环，会过滤掉自己插入的节点。
4. **fetch 拦截读真实模型** —— 官方解析 SSE 时会丢掉 `message.model`，
   旁路层克隆响应流自行解析，把真实模型名补进消息的 `serverModel` 字段。
   只拦截 `/messages`，不影响 `/models` 等其他请求。
5. **模型取值器** —— 官方把默认模型写死为 `deepseek-flash`。补丁在其定义处加了一个
   `ec0()` 取值器（优先读 `localStorage['chat-demo:model']`），并把 3 处调用点改为调用它。
   之所以用显式调用而不是把变量换成函数，是因为 `{model: ec}` 这类取值会把**函数对象**本身
   传出去。
6. **多提供方镜像** —— 官方只读 `chat-demo:api-base` 与 `chat-demo:api-key` 两个**单值槽位**，
   所以「设为默认提供方」= 把该提供方的地址/Key/默认模型镜像进这些槽位。
   好处是 bundle 端无需理解「多提供方」，改动面最小。
7. **API Key 回收与对账（防「Key 无效」）** —— 官方自带的界面（数据管理里的
   Key 编辑框）会直接把 Key 写进 `localStorage`，桥接层看不到这个过程。因此：
   - 启动时把「应用里已有的 Key」**回收进当前提供方**；
   - 运行期间每秒**对账一次**，官方面板改了 Key 就采纳进提供方；
   - 保存设置时**不允许用空值覆盖**已有的 Key。
   不做这些就会出现：设置面板显示「尚未填写 API Key」，
   用户在面板里点一次保存，就用空 Key 覆盖掉原本可用的 Key，
   之后每次启动都被判定「API Key 无效」。
8. **设置区块只挂「通用设置」** —— 官方两个标签页（通用设置 / 数据管理）
   共用**同一个**内容容器 `.content-_85c1b`，靠切换子节点换页，
   而弹窗默认可能停在「数据管理」。所以不能无脑 append，
   必须先判断当前激活的标签页：只有「通用设置」才挂，切到别的标签页就摘掉，
   否则两块内容会**串台**。
9. **模型菜单挂到 body** —— 输入区外层容器有 `overflow:hidden`，
   菜单若留在输入区内，向上弹出时会被**裁断**；因此菜单挂在 `document.body` 上并用
   `position:fixed` 定位。滚动时菜单**跟随按钮移动**而不是关闭，
   但菜单**自身内部**的滚动会被忽略（否则翻列表会把内容顶回顶部）。
10. **设置自动回填的判定（跨浏览器同步的关键修复）** —— 早期实现用
    「白名单里一个键都没有」来判断本机是不是全新浏览器，**这个判据是错的**：
    桥接层自己在启动时就会写入 `chat-demo:active-provider` 与 `chat-demo:model`，
    所以白名单永远不为空，**自动回填从来没有触发过**。
    现在改为「同步标记 + 时间戳」：
    - 本机从没同步过 → 无条件采纳文件夹里的设置；
    - 已同步过 → 只有文件夹里的更新时间更晚才采纳。

    对应地，`数据/apikey.json` 与 `数据/settings.json` 写入时会记录
    `chat-demo:settings-synced-at`，作为「本机已同步」的凭据。
11. **全新浏览器自动读回对话** —— 判断条件是「没有历史同步标记」**且**
    「本地库是空的」，两个都成立才自动恢复，因此对老用户完全无感。
12. **空库快照的防丢失闸门** —— 快照是「全量重写 + 清理多余文件」，
    所以一个**空库**在全新浏览器里跑一次，就会把文件夹里的历史对话成批删掉 ——
    与「防丢失」的目的完全相反。现在加了闸门：
    本地没有对话、文件夹里有存档、且本机没有历史同步标记时，**跳过清理**，
    并在 `数据/manifest.json` 里记 `pruneSkipped: true`。
    只有确认对过账之后才允许清理。
13. **刷新闪动的根因与「不再刷新」** —— 官方在**启动时**把 API Key 读进一个内存
    store，之后发消息、传文件、语音转写都取那份**快照**。所以「启动之后改 Key」
    一律不生效，只能刷新页面 —— 而刷新既闪一下，又会把当前打开的对话丢掉
    （官方不记录「开着哪个对话」）。两处修复：
    - 补丁在模型取值器旁又加了一个 `k0()`（同样优先读 `localStorage`），
      把 5 处「取 Key」的调用点改为 `k0()`，于是**换 Key / 换提供方即时生效**；
    - 桥接层的切换提供方与切换模型**不再调用 `location.reload()`**。

    另外，早期版本还有一个**刷新死循环**：快照每次都会用新的 `savedAt` 重写
    `数据/settings.json`，于是「文件夹比本机新」恒成立，每次启动都要求刷新。
    现在 `applySettings` 把「写入相同值」视为无改动，
    `hydrateSettingsFromFolder` 也**先比内容、后比时间戳**，
    并且 `requestReload()` 有 8 秒节流闸门（同一时间窗内只允许自动刷新一次）。
14. **深链接** —— 官方完全没有「当前对话」的概念，于是旁路层按侧边栏标题生成
    token（重复标题记为 `title#2`），映射表存在
    `localStorage['chat-demo:deeplink-tokens']`，地址栏用 `#c=<token>` 表示当前对话，
    刷新后据此自动点回原对话。token **一旦生成就不再变化**。
15. **`addProvider()` 不是只给测试用的** —— 导出接口里的 `getProviders()` 返回的是
    **防御性拷贝**（避免外部改坏内部状态），所以外部直接 `push` 列表是无效的。
    要新增提供方请用 `addProvider(spec)` 或 `updateProvider(id, patch)`。
16. **API 地址里绝不能重复 `/anthropic`** —— 应用自己会拼
    `/anthropic/v1/messages`、`/anthropic/v1/files`（文件上传）以及 `/models`。
    所以 `m` 必须是**裸根地址**，`g` 才是 `${m}/anthropic/v1`。

    这里踩过一次坑：早期的补丁把 `m` 规范化成了「带 `/anthropic` 的地址」，
    却仍然写 `${m}/anthropic/v1`，于是 `g` 变成 `/anthropic/anthropic/v1`。
    症状很有迷惑性 —— **`/models` 能通**（它只用 `m`），但**文件上传必定失败**
    （它用 `g`）。现在两侧都归一化：

    - bundle 端：`m` 会剥掉结尾的 `/anthropic`（也会剥掉 `/anthropic/v1`）；
    - 桥接层：新增 `normalizeBase()`，填地址、保存提供方、读旧配置时都过一遍。

    在地址栏里写 `https://host/anthropic`、`https://host/anthropic/v1`
    或 `https://host/` 都可以，最终都会收敛到 `https://host`。
17. **上传失败的瞬时重试** —— 实测碰到过 `net::ERR_HTTP2_PROTOCOL_ERROR`：
    地址与请求体都没问题（同一个请求用 `curl` 打过去能正常返回 401，说明端点存在、
    参数合法、CORS 也配好了），是浏览器与服务端之间的 HTTP/2 连接被中途掐断。
    这类故障是**瞬时**的，重试一两次通常就好了。所以 fetch hook 里对
    `POST .../files` 加了重试（最多 3 次，退避 400ms/800ms）：

    - 只重试**网络层**错误（`TypeError` / `ERR_HTTP2` 等）；
    - 4xx/5xx 是服务端明确拒绝，重试没意义，直接放行让应用显示真实原因。

    如果你的中转站只实现了 `/messages` 而没实现 `/files`，那会稳定失败 ——
    这种情况只能换提供方，或在发消息时改用文本粘贴内容。
18. **启动遮罩（消掉刷新闪动）** —— 带 `#c=` 刷新时，应用在挂载阶段**一定**会先
    渲染一次空对话（「今天有什么可以帮到你？」），我们只能在其后按 token 点回去。
    这段窗口实测约 200~400ms，足以看到闪动。做法：
    - 探测从固定 250ms 轮询改为 `MutationObserver` + 100ms 兜底，
      侧边栏一出现就动手；
    - 只在 React 的 `onClick` 已经挂上（`__reactProps$` 里有 onClick）时才点击，
      否则 `click()` 是空转；
    - 启动 token 单独记一份 `bootToken`，因为应用挂载时会把 `location.hash` 抹掉，
      否则会中途丢失目标；
    - 恢复期间**不**向地址栏回写，避免覆盖带过来的 `#c=`；
    - 同时铺一层跟随主题色的全屏遮罩，恢复完成（或 3 秒超时）后淡出。
19. **桥接脚本的缓存击穿** —— 应用自己的产物（`main.6fd9c886.js` 等）文件名带内容
    哈希，改了就换 URL，浏览器不会用旧的。而 `localstore-bridge.js` 是**固定名**：
    浏览器或静态服务器一旦缓存，就会一直跑旧版本 —— 症状是「代码明明改了、
    也刷新了，但页面行为一点没变」，极难自查。
    现在 `apply-patch.mjs` 每次按桥接脚本内容算一个 FNV-1a 短哈希写进标签
    （`localstore-bridge.js?v=a3b2b78b`），并处理三种历史形态：
    无哈希旧标签 → 升级；重复注入 → 收敛为 1 份；哈希过期 → 重算。
    `verify-patch.mjs` 会校验标签哈希与脚本内容一致，不一致就报错提醒重跑补丁。
20. **界面动效层（`localstore-motion.css`）** —— 动效**没有**写进应用的 CSS，而是
    单独成一个文件、由桥接层运行时注入。原因：应用是压缩产物、类名是哈希的，
    直接改会在下次升级时全部作废；独立成文件后既能随时调整，也对原始产物零改动。

    规则全部挂在 `html.ls-motion` 之下，所以关掉开关只要摘掉一个类，
    不会留一堆半生效的规则。设置面板「通用设置 → 界面动效」可以开关，
    也可以直接调 `window.__localstore.setMotion(false)`。

    三条实测结论决定了这里的实现方式（都是先探针查证、再写代码）：

    | 现象 | 后果 |
    | --- | --- |
    | 弹窗与侧栏在关闭/折叠时是**从 DOM 移除**的（`overlayExists:false`、`siderExists:false`） | 移除了就没有过渡可做，只能做**入场**动画 |
    | 设置页两个 tab **复用同一个** `content-_85c1b` 节点、只换子元素 | 给容器做动画无效，要针对 `> *` |
    | `scroll-_7ccaf` 的计算样式是 `display: contents`（自身 0×0） | 给它加动画完全看不出来，真正有盒子的是 `column-_7ccaf` |

    另外确认过应用自带 CSS 里**没有任何 `transition: all`**（575 条规则全查过），
    所以这层补丁不会和原有过渡打架。动画只用 `opacity` / `transform`，
    不碰 `width` / `height`，避免触发布局重排掉帧；列表错开延迟按 8 项封顶，
    否则长列表会「越往下越晚出现」。

    最后，`prefers-reduced-motion: reduce` 下会关掉全部动画并取消位移/缩放
    （保留颜色过渡，因为颜色变化不会引起前庭不适）。这是硬性要求，不是可选项。
21. **侧栏收起为什么要「替身」** —— 这一块返工过多次，把结论记下来。
    ⚠ **先看第 22 条**：那之后又按用户思路改成了「收起 = 展开的倒放」，
    替身的角色缩小成「只负责布局宽度」，视觉退场交给内容层的镜像关键帧。
    下面记的是为什么需要替身、以及做替身时踩过的坑，仍然成立。
    应用点「收起边栏」时是把 `.sider-ac14ac` **整个从 DOM 移除**
    （实测 `frame` 的子节点只剩 `.main`），所以没有节点可做过渡。

    更麻烦的是主内容区**不能**用 `transition: width` 补动画：它带
    `flex: 1 1 0%`，宽度由 flex 布局算出来，连内联 `width: 900px` 都改不动它
    （逐帧实测：设了也不生效），因此宽度过渡永远不会触发。结果就是真侧栏被移除的
    瞬间主区就弹满全宽（约 7ms），侧栏还在慢慢动 —— 观感就是「回弹一下」。

    最终做法参考了 `collection/layout.css` 里 `.sidebar.collapsed` 的思路
    ——**让侧栏这一侧做宽度过渡**（它是 `flex: 0 0 auto`，宽度就是它的布局尺寸），
    主内容区自然会跟着逐帧重排：
    - 在点击的**捕获阶段**（早于 React）把真侧栏 `visibility:hidden`；
    - 在**同一个 flex 位置**插入一个同宽的替身，锁住内层尺寸 + `overflow:hidden`；
    - 下一帧把替身宽度过渡到 0（过渡属性集合照抄参考实现：`width`/`min-width`
      一起过渡，否则 `min-width` 会把宽度卡住；`opacity` 负责淡出）；
    - `transitionend` 清理 + `setTimeout` 兜底（减弱动效时不会有 `transitionend`，
      只靠事件会留下一个永久占位的节点）。

    踩过的两个坑：
    - 一开始用 `setInterval` 轮询判断侧栏在不在，而选择器 `querySelector('.sider-ac14ac')`
      会命中**替身克隆体内部**的同名节点，于是每轮都误判成「侧栏又挂载了」，
      无限生成替身（实测每 300ms 一次）。现在改成事件驱动 + `closest()` 排除替身。
    - 曾经直接给 `.main-_9fdf5` 加 `transition: width`，完全没用（原因见上）。
      测这类问题必须**逐帧采样**才看得出来，光看最终状态是发现不了的。

    **替身自己必须会画背景。** 这是「收起时左边多出一块奇怪东西」的根因：
    最初只克隆了内部结构，外层 wrapper 是透明的 —— 宽度一收，**让出去的那部分
    就露出 frame 的更深底色**（`#151517` vs 侧栏的 `#1b1b1c`），看着就像左边
    凭空浮出一块。真侧栏的填充色在 `.sider` 自身上，克隆体内层虽然有，
    但外层变窄后内层也被裁掉了。所以要把背景、`border-right`、`padding`
    一并从真身现读后写到 wrapper 上（现读而不写死，主题/令牌变了能跟着变）。
    注意紧接着的第二个坑：**写了 padding/border 就必须同时照抄 `box-sizing`**，
    否则 `width` 会再叠上它们，量出来比真身宽（实测 286 vs 261），
    接管当帧直接跳一下。真侧栏自带 `border-box`，照抄即可。

    **展开侧方向相反，做法也不一样。** 展开时应用重新挂载 `.sider` 是瞬时的，
    主内容区会在同一帧从 1378 跳到 1117，而侧栏只是 `translate` 滑入（宽度恒为 261）
    —— 逐帧实测 `e0` 就已经是最终值，之后 16 帧不再变化，观感就是「中间那块突变」。
    这里**不能**像收起那样另插一个占位替身：替身撑开与真实 sider 挂载是两个独立时序，
    中间会空出一段「占位已满、侧栏还没露面」的空白（实测 520ms 内左边全是纯背景色）。
    最终改为**直接接管 sider 自身的宽度**：它挂回来时先设 0 宽、强制结算一次，
    再放开到 261px 让它过渡过去 —— 两边天然同步，也没有空窗。
    结束时把内联的 `width` / `transition` 清掉，交还给应用自己的样式。
    实测主区左边缘：`25,25,25,62,119,169,202,225,240,250,257,260,261…`（11 个不同值、单调、单帧最大 58px）。
22. **收起 = 展开的倒放（用户提的思路，一把解决三个老毛病）。**
    之前那套替身方案能跑，但观感一直不对：用户连续反馈过
    「文字从左边滑过来」「闪一下」「闪很多下」，最后直接给了思路 ——
    *收起完全复用展开的动画、只是倒过来放*。**这个思路是对的**，
    实现之后用户的原话是「对味了！！！」。

    倒放要成立，必须凑齐三件事，缺一件就不像逆过程：

    - **内容层播镜像关键帧。** 新增 `@keyframes ls-sider-out`，
      它就是 `ls-sider-in` 的严格反向（`opacity 1→0` 配
      `translate3d(0,0,0) → translate3d(-100%,0,0)`）。
    - **缓动必须是严格的时间反演。** 判据由用户点明：
      **「在同一位置，展开和收起的速度要一样」**。
      形式化即 `C(s) = 1 - E(1-s)`，等价于 **`E(t) + C(1-t) = 1`** 恒成立。
      这既是「位置一样 ⇒ 速度一样」的充要条件，也是「倒放」的唯一定义。
      对应两个令牌：`--ls-motion-sider-ease-in` / `-ease-out`。
    - **两边时长一致**（都用 `--ls-motion-sider` = `0.26s`，
      与 `--ls-motion-enter` 对齐），否则时间轴上对不齐。

    ⚠ **反演曲线要数值拟合，不要在纸上推控制点公式。**
    这一条返工了三次，每次都是「凭手感挑曲线」，记录如下：

    | 尝试 | 曲线 | 与目标偏差 | 结果 |
    | --- | --- | --- | --- |
    | 1 | `cubic-bezier(0, 0.7, 0.84, 1)` 点对称镜像 | 0.80 | 用户：「收起是先快后慢，应该先慢后快才对」 |
    | 2 | `cubic-bezier(0.42, 0, 1, 1)` 标准 ease-in | 0.45 | 只是「形状像」，不是反演 |
    | 3 | `cubic-bezier(0, 0.84, 0.3, 1)` 按「交换端点」推的公式 | **0.92** | 实测仍是先快后慢，被 e2e 断言当场抓住 |
    | 4 | `cubic-bezier(0.776, 0, 0.816, 0)` 数值拟合 | **0.019** | ✔ |

    点对称镜像（第 1 次）错在哪：它的走势与展开**同向**（都前重后轻），
    所以两段动画看着速度差不多，根本没有「倒过来」的感觉。
    第 3 次错在哪：我推的 `(x1,y1,x2,y2) → (1-y2,1-x2,1-y1,1-x1)` 公式不对
    —— 它给出 0.92 的偏差，几乎等于没错。正确做法是拿同一套贝塞尔数学
    直接算目标 `C(s) = 1 - E(1-s)`，再在四参数空间粗搜 + 细化拟合。

    为什么反演出来这么极端：展开起手极快（前 10% 就走掉 49% 的位移），
    所以倒着走必然是「开头几乎不动、末段猛冲」。逐段增量（每 10% 占比）：
    ```
      展开 E : 0.49 0.26 0.13 0.06 0.03 0.02 0.01 0.00 0.00 0.00
      收起 C : 0.00 0.00 0.00 0.01 0.01 0.03 0.06 0.12 0.28 0.49
    ```
    把 E 的增量序列反向读就是 C —— 这才是「倒放」。
    实测也确实如此（`probe-v61`，面板宽度）：
    `28ms 261 → 96ms 261 → 138ms 259 → 188ms 250 → 237ms 214 → 285ms 130`。

    ⚠ 由此带来一个**已知的观感代价**：正因为它严格反演，展开入口那种
    「瞬间冲进来」在收起时会变成「先愣一下再猛收到底」。
    实测前 150ms 面板宽度基本不动（261 → 259）。这是数学的必然结果，
    不是 bug。若哪天想换成「匀速」，只需把 `-ease-out` 改成 `linear`，
    但那样就不再满足 `E(t)+C(1-t)=1`，`e2e-motion` 的
    「同一位置展开与收起速度一致」断言会失败 —— 那条断言就是为守住
    这个取舍而写的，改之前先确认是不是真的要放弃倒放。

    结构上有个必须注意的点：**内容层要 `position: absolute`**。
    它的宽度被内联钉在 261（防止内容重排），若还留在文档流里就会把 wrapper
    撑到 261，wrapper 根本收不到 0。所以让它脱离流，由 wrapper 自己的
    `width` 过渡去驱动主内容区重排。wrapper 则要 `position: relative`
    给内容层做定位上下文（它**没有**脱离流，仍是 frame 的 flex 子项，
    所以「替身在 flex 流里」那条断言仍成立）。

    于是分工变成：**wrapper 管布局（宽度收拢），内容层管视觉（左移淡出）**，
    两者共用同一时长与同一条反演缓动，天然同步。
    wrapper 一直画着侧栏底色，所以内容淡出后剩下的是「一块收拢的面板」，
    不会闪出 frame 的更深底色。

    实测轨迹（`probe-v59`）：收起 `tx 0 → -251.3`、`opacity 1 → 0.04`、
    面板 `261 → 10`；展开 `tx -25 → 0`、`opacity 0 → 1`、面板 `25 → 261`。
    `e2e-motion` 第 [8] 组九条断言锁住这个关系，其中最关键的一条是
    「同一位置展开与收起速度一致（E(t) + C(1-t) = 1）」。

    测这块要注意两个环境坑：
    - **采样必须完全在页面内调度**。每帧 `await` 一次 CDP `evaluate`
      只能采到个位数帧；`requestAnimationFrame` 在 headless 下被节流得更狠。
      用页面内的 `setTimeout(step, 10)` 一次 `evaluate` 采完。
    - **`getComputedStyle` 对 `contain: paint` 子树里的 transform
      约 50ms 才刷新一次**（实测同一段动画有时只给 3 个不同值）。
      所以断言进度要用 `getBoundingClientRect().width`（每次都取真实布局值），
      不要用 transform 的插值。另外 `transitionend` 一到就会把替身删掉，
      采样窗口要留在它之前（`SIDER_COLLAPSE_MS + 260` = 520ms）。

    **仍然要防的老坑：入场动画的选择器绝对不能漏到替身的克隆体上。**
    克隆体来自真侧栏的 `outerHTML`，**带着一模一样的 class**，
    所以任何按 class 命中的动画规则都会在替身插入的瞬间被克隆体重播一遍。
    - 规则必须写成 `.ls-motion .frame-_9fdf5 > .sider-ac14ac`（注意那个 `>`）。
      真侧栏是 frame 的**直系子节点**，克隆体被包在 `.ls-sider-ghost` 里，
      加了 `>` 就天然排除了。曾经同时存在一条**不带 `>` 的**
      `html[data-ls-sider-anim='enter'] .sider-ac14ac`，它匹配 `<html>` 下全部
      `.sider-ac14ac`，于是收起时克隆体照样播 `ls-sider-in`
      （整块从 `translate3d(-100%,0,0)` 滑回来 + `opacity` 0→1）。
    - 侧栏**内部**的列表项也自带 `ls-item-in`，还带 0/16/32/48ms 的错峰延迟，
      克隆体一插入就全部重播 —— 这就是「闪很多下」。
      内容层现在显式声明 `animation: ls-sider-out …`，只播这一条，
      内部那些错峰动画不会被继承过去（`animation` 不可继承）。
    - `expandSider` 在「sider 已经挂载」时是 `start(existing); return;`，
      **走不到 `cleanup()`**，所以 `data-ls-sider-anim` 会一直留在 `<html>` 上。
      现在 `start()` 的 `transitionend` 和 `collapseSider` 开头都清一次。

    **交接要像素级无缝。** `collapseSider` 第一件事就是 `setSiderAnim(null)`：
    既防止展开动画残留，也保证真身回到**自然几何**再克隆
    （否则克隆到的是动画中间态，对不上就闪）。内边距照抄真身、
    `margin-left` 归零 —— 实测替身插入当帧面板与标题的
    `left/width/opacity` 差值全为 `0.0`。
23. **收起后左侧那条「背景色」曾经被误判为应用固有**，其实是我们自己的 bug：
    替身 wrapper 一开始是透明的，让出去的那块露出 frame 的更深底色
    （`#151517` vs 侧栏的 `#1b1b1c`）。已在第 21 条里修掉（现读真身的
    背景/边框/内边距写上去）。**不要再按「固有」理解它。**
    排查这类问题的通用办法仍然有效：把动效关掉跑一遍原生行为做对照。
24. **附件上传的两类瞬时故障都会重试**（原来只重试网络层错误）：
    - 网络层被掐断 —— fetch 统一抛 `TypeError`；
    - 服务端临时故障 —— `429` 与 `5xx`。
    两者在「重试一次就好」这点上没有区别，所以一并重试；明确拒绝的 4xx
    （401/400 等）不重试，直接放行让应用显示真实原因。
25. **测试里模拟网络故障要用 5xx，别用 `socket.destroy()`。**
    这是 `e2e-upload-retry.mjs` 反复随机失败的根因：销毁 socket 之后，
    **Chrome 会自己在底层静默重连重发**，应用侧的 `fetch` 有时根本看不到失败
    —— 实测服务端明明掐断 2 次，客户端诊断日志里只有 1 次失败、甚至一次都没有。
    于是断言结果取决于浏览器的透明重试策略，时绿时红。
    改成让服务端返回 `503` 后，应用层可见且完全确定。
    网络层那条路径仍要覆盖，但只断言「最终成功」，不断言观测到的失败次数。
    另外，模拟端点必须放在能匹配桥接层 `/\/files(\?|$)/` 的路径上，
    否则请求根本不会被接管（`/__flaky-files` 看着像其实不匹配，白测一轮）。
26. **品牌外观层（`localstore-brand.css`）+ 开屏标语随机化** ——
    换 logo、随机标语都在这一层，与动效层分开：
    动效可以被设置里的开关关掉，但品牌标识属于外观本身，**没有开关**。
    做法一律是「加伪元素 / 盖一层」，不删官方节点（删了 React 下次渲染又回来）。

    ⚠ **鲸鱼图标只保留一只。** 折叠态的按钮组里官方原本给两个按钮各配了一只
    鲸鱼（`打开边栏` 和 `开启新对话`），用户要求删掉多余的那只。
    现在 `::before` 只挂在 `button[aria-label="打开边栏"]` / `"Open sidebar"` 上，
    `开启新对话` / `"New chat"` 显式写 `content: none !important; display: none !important;`。
    连带修了折叠态按钮组的左边距（`.ls-brand .collapsed-ac14ac { left: 16px }`）——
    原来为第二只鲸鱼留了位置，删掉后按钮偏右，看着像没对齐。
    **测试要注意**：`e2e-features.mjs` 里原来有三条断言写的是「两只鲸鱼」，
    现在改成「只有一只、且完整落在侧栏可视区内、折叠态按钮组在官方站位」。
    改这类断言前先确认是**预期的行为变更**而不是回归。

    **另一个坑：应用名会被上游/本地化写回。** 官方那个 `API 使用 demo` 字样
    出现在 `.appName-ac14ac` 里，直接改文本会被 React 的下一次渲染写回，
    而且换语言时还会被 i18n 再覆盖一次。所以 `applyAppName()` 的做法是：
    每次渲染后都用 rAF 节流检查一遍，只有在文本已经是目标值（`DeepSeek`）
    且带 `data-ls-appname` 时才早退，否则重新写入并打标记 —— 自愈式，
    不依赖「改一次就永远生效」。它挂在 `watchMessages()` 的观察器回调里，
    另外 `watchMessages()` 结尾也调一次（首屏那次没有 DOM 变动，观察器不会触发）。

    三个踩过的坑：
    - **伪元素必须显式写 `display`。** 只给 `content:''` + `width/height` 时，
      实测 `display` 的计算值会落到 `none` —— 图标完全不出现，
      而 `mask-image`、`background-color` 全都是对的，光看这些属性会以为没问题。
      （用 `CSS.getMatchedStylesForNode` 查也查不出是谁设的 none，加
      `display:block` 就好。）测这类东西要**读 `getComputedStyle(el,'::before').display`**，
      别看属性表里有没有这条规则。
    - **开屏标语不能直接改官方那个文本节点。** 改完 React 的下一次渲染会写回原文
      —— 实测轮询 7 秒，一次都没留住。正确做法是：给 greeting 加 `.ls-greeting-random`
      并用 `font-size:0` 收起官方文字，再插入一个 `[data-ls-greeting]` 的 span 承载文案。
      React 只认识它自己的文本节点，碰不到这个外来节点，所以能稳定留住。
      验证时**不要用 `textContent`**（它会把被收起的官方文字也算进去，看着像没生效），
      要量官方文本节点的 `Range.getBoundingClientRect().width === 0` 和 span 的字号。
    - **内置提供方改名要连带归一化旧数据。** 只改 `OFFICIAL_PROVIDER.name`
      不够：老浏览器里 `chat-demo:providers` 已经把旧名字持久化了，
      读回来还是旧的。`loadProviders()` 里用 `normalizeBuiltinName()` 顺手改掉，
      且**只认旧默认名**，用户自己起过的名字不会被覆盖。

    标语池就在 `GREETING_POOL` / `GREETING_TIMED` 两个数组里（照抄用户给的候选）。
    时段问候的前缀按时段替换，避免出现「晚上好，今天有什么计划？」这种
    实际时刻与问候不搭的说法。
27. **功能扩展层（`localstore-features.js` / `.css`）—— 7 项功能都在这两个文件里。**
    由桥接层的 `installFeatures()` 动态插入（`<link id="localstore-features-css">` +
    `<script id="localstore-features-js">`），插在 `boot()` 的 `installBrand()` 之后。
    独立成文件而不是塞进桥接层，是因为这些功能大量依赖应用的 hash 类名、最容易随
    升级失效 —— 升级时只需检查这一个文件的常量区（`SEL`、`ICON`、`LS_*`）。
    功能清单：① 右侧消息索引轨道 ② 置顶对话 ③ 长消息折叠 ④ 过大粘贴转附件
    ⑤ 关键词搜索对话 ⑥ 对话内换模型（每个对话各记各的）⑦ 版本角标 `<xx/xx>`。

    **这一层踩过的坑（按踩到的顺序）：**

    - **一个功能抛异常会静默干掉后面所有功能。** `applyAll` 原来用 `throttled()`
      把整个函数体包在一个 try/catch 里，所以任何一步抛错，**后面的步骤全部跳过**，
      表现成「某个按钮就是不出现」，控制台只有一行 warn。
      现在每步独立 `step(name, fn)` 各自 try/catch。
      同理，`top.insertBefore(btn, collapseBtn)` 因为收起按钮在
      `<span class="trigger-_94788">` 里而不是 `top` 的直接子节点而抛错，
      异常被吞掉的表现就是「搜索按钮永远不出现」。
    - **每帧改 DOM 会饿死 300ms 的防抖挂载。** 置顶排序原来无条件对每个侧栏项
      `appendChild`，而 `appendChild` 对已挂载的节点等于「摘下来再插回去」，
      每次都是一个 childList 变动 → MutationObserver 回调 →
      桥接层的 `scheduleComposer()` 防抖（300ms）被无限重置 →
      `mountComposer()` 永远不执行 → **模型选择框整个消失、侧栏也不刷新**。
      实测 18 秒里 `scheduleComposer` 触发 1080 次、`mountComposer` 0 次。
      修法：先比较目标顺序与当前顺序，真不一样才动 DOM。
      排查这类问题最快的办法就是数 `scheduleComposer` / `mountComposer` 的调用次数。
    - **`display:none` 一旦被卡住就不会自己恢复。** 桥接层的 `placeComposer()` 在
      「输入行几何是中间态」时会算成「放不下」并 `display:none`，之后几何恢复了，
      但 rAF 循环每次都在这一分支提前 return，按钮就永久不显示 ——
      用户看到的是「切换对话后模型选择框就没有了」。
      现在除了 120ms 重试，还加了一个看门狗：连续 3 帧都是 `none` 就强行摘掉并重排。
    - **悬浮提示会被旁边按钮的提示串味。** 搜索按钮必须紧挨收起按钮左边，而应用把
      「收起边栏」提示的触发区算成了一个覆盖两个按钮的矩形，于是悬浮搜索按钮时
      应用会同时弹出「收起边栏」，和我们自绘的提示叠在同一位置（两者都是 64×26）。
      修法：悬浮搜索按钮时给 `<html>` 打 `data-ls-search-hover`，用 CSS 把
      `.tooltip-_94788` 藏起来。**`CSS :has()` 在这里不可靠，实测不生效**，要用 JS 打标记。
    - **全站只有一个 `.ls-tip` 节点，谁都能把它收掉。** 轨道重建（`removeRail`）会调
      `hideTip()`，而重建可能发生在任何一次 DOM 变动时，结果悬浮搜索按钮刚弹出的
      「搜索对话」被顺手收掉 —— 表现成「搜索按钮没有提示」。
      现在 `hideTip(owner)` 会核对归属，各功能只收自己的提示。
    - **换模型会被提供方的 `defaultModel` 冲掉。** 桥接层 `selectModel` →
      `applyActiveProvider` 最后有一句 `if (p.defaultModel) lsSet(LS_MODEL, ...)`，
      所以「只写 `chat-demo:model`」的恢复方式会被立刻覆盖。
      `selectModel` 里本身有 `p.defaultModel = model`，所以恢复必须走 `selectModel`。
      又因为这个赋值，**提供方的 `defaultModel` 会随每次换模型漂移**，
      不能拿它当「新对话用哪个模型」的基准 —— 否则会出现「模型串味」：
      在甲对话选了 v4-pro，切到从没打开过的乙对话，乙也被登记成 v4-pro。
      现在基准值用 `chat-demo:ls-default-model` 存一份安装时的快照。
    - **切换对话的模型记忆有竞态。** 点侧栏时，「active 高亮」先变、对话内容后加载，
      中间有一段「标题已变但消息还是旧的」的窗口，此时记录会把模型写到错误的对话上。
      另外 `markSwitching` 里**不要**顺手改 `convModel.activeTitle`：改了之后
      `applyConvModel` 会发现「标题没变」而直接 return，模型永远不恢复。
      现在的路径是「点侧栏 → 立刻用点击项的标题 `applyModelForTitle`」，
      `activeTitle` 只在真正处理过之后才更新。
    - **平滑滚动不能用固定延时等。** 轨道定位原来写 `setTimeout(syncRailActive, 900)`，
      但应用的平滑滚动在无头 Chrome 下 3 秒都没停，900ms 时算出的「视口顶部那条」
      还是上面的消息 —— 点第 7 条、高亮第 5 条，而且之后不再纠正。
      现在用「连续 6 次采样 scrollTop 没变」判定停稳。
      另外目标会被滚到离容器顶约 24px，而判定阈值是 `scrollTop + 8`，
      这 16px 的差吃不掉，所以点击结果还要「钉住」（`pinnedIndex`），
      用户自己滚动超过 120px 才解除。
      判断「用户滚走了没有」要拿 scrollTop 和程序落点比，
      **不能**用「目标消息离容器顶多远」—— 目标在视口下方时那个值是 -900 多，
      从点击那一刻就会被误判成「用户滚走了」。
    - **`syncRailActive` 里不能 `break`。** 下方还没被应用渲染出来的消息
      `offsetTop` 可能是 0，一 break 序号就停在很靠前的位置，高亮跟着错。
      要全扫一遍取最大序号。
28. **轨道只显示用户提问。** 一条横线 == 一条用户提问，助手回答不进轨道；
    不要框框（轨道本身无背景/无边框/无圆角），横线用伪元素画；
    悬浮显示该条提问原文。`data-ls-index` 存的是「在全部消息里的真实序号」（1、3、5…），
    点击定位靠它，不要当成轨道内的下标。
29. **过大粘贴自动转成附件（功能 ④）—— 这是"零自造 UI"的功能。**
    用户的原话：「你不用自己写 ui，也不用加提示语，你就直接用原生的东西，
    相当于拖了一个 txt 文本文档进来一样的」。

    所以这一版**故意没有任何样式**（`localstore-features.css` 里那一段是注释占位，
    原来的 `.ls-paste-*` 托盘样式全部删掉了）。旧实现是自己画一个「粘贴区」托盘 +
    「粘贴原文至输入框」按钮 + 自己存的 `chat-demo:ls-pasted-texts`，
    用户明确否掉了。现在的路径完全走应用自己的能力：

    - 监听捕获阶段的 `paste` 事件（`installPasteGuard()`）；
    - 内容够大（`PASTE_MIN_CHARS = 1200` 或 `PASTE_MIN_LINES = 16`，两者取或）才算；
    - `findUploadInput()` 找应用那个隐藏的 `<input type=file multiple>` ——
      **必须跳过 `accept` 里带 `.zip` 的那个**（那是"导入历史"的输入框），
      优先选带 `multiple` 的；
    - `new DataTransfer()` → 塞一个 `new File([text], '粘贴的文本（N）.txt', {type:'text/plain'})`
      → 赋给 `input.files` → 派发 `change`。这就是"拖了个 txt 进来"的全过程，
      剩下的缩略图、删除按钮、上传逻辑全是应用自己的。

    几个细节：文件名多段时是 `粘贴的文本（1）.txt`、`粘贴的文本（2）.txt`
    （**全角括号**，序号存在 `chat-demo:ls-paste-seq`）；
    任何一步失败都返回 `false`，让这次粘贴**照常落进输入框**
    （宁可退回官方行为，也不能把用户的粘贴弄丢）。
    测试断言的是 `ownUiNodes === 0` —— 界面上不能有我们自己的粘贴 UI，
    有就说明 UI 又长回来了。

30. **置顶对话是一个独立分节，不是「提到最前」。**
    用户的原话是「移到最上面，相当于一个新的日期（跟"今天""昨天""7天前""30天前"一样），
    显示"置顶"，置顶的全部对话按照最后一条发送的消息时间排序」，后来又加了
    「可以展开收起，旁边加一个类似 ^ 的符号，整行都可以点击，收起后显示"置顶 xx 个对话"」。
    实现要点与坑：
    - **不能把真身搬进自造的小节。** 侧栏是 React 渲染的，React 按它自己的顺序
      `insertBefore`，搬过去会被搬回来，来回搬就是每帧一次 DOM 变动
      （这个死循环踩过，后果是模型选择框整个消失）。
      现在的做法是：真身留在原日期分节里、用 `display:none` 藏起来占位，
      「置顶」小节里放**克隆**。
    - **克隆必须清掉 `__reactFiber$…` / `__reactProps$…`。**
      `cloneNode(true)` 会把这些键一起浅拷贝过去；带着它们的克隆被 React 的事件
      系统扫到会去对应 fiber 上找 props，结果是「点克隆触发了别人的 onClick」
      或者直接报错。见 `notReactOwned()`。
    - **点克隆要自己接管跳转。** 清掉 React 属性之后点它没有任何反应。
      另外 `openSessionByTitle()` 里**必须跳过克隆**：它在列表最前面，
      顺序找到的第一个匹配项正好是克隆，`click()` 静默无效 ——
      表现成「点置顶里的对话打不开」。
    - **排序用 `sessionSummaries.updatedAt`**（语义上就是最后一条消息的时间，
      桥接层每次写库后都会更新），拿不到时间的沉到最下面。
      缓存由桥接层派发的 `localstore-changed` 事件作废。
    - **展开/收起动画用 Web Animations API，动画做在包裹层上。**
      内容高度随置顶条数变化，CSS transition 需要一个写死的 max-height
      （写大了动画会卡一下，写小了内容被裁），而且收起态是 `display:none`
      量不出目标高度。所以正文外面包一层 `.ls-pin-body`，
      量出「展开高度」之后 `animate([{height: from}, {height: to}])`，
      并且**不加 `fill: 'forwards'`** —— 播完自动回到样式表状态，
      不留内联样式（`renderPinnedSection` 每轮 Mutation 都会跑，
      留内联高度会把后续测量全带偏）。
    - **`^` 用 transform 翻转，不要换 path**（换 path 没法过渡）。
    - 收起状态存在 `chat-demo:ls-pin-open`，刷新后保持。
    - 置顶项标题**不加粗**（用户明确说「可以不用加粗」）。
    - **置顶行必须保留「...」，否则没法取消置顶。** 菜单里那一项
      （`取消置顶` / `置顶`）是我们插进官方菜单的（`decorateMenu()`）。
      曾经为了「克隆的按钮点不动」把 `...` 整个剥掉，用户立刻指出
      「置顶的也要有…，不然无法取消置顶」——所以现在是保留 + 接管点击。

    **★★ 三个「在跳 / 点不开」类 bug 的根因（都修好了，改动很微妙，别回退）★★**

    **(1) 每轮重放都删掉重建克隆 → 到处乱跳。**
    `startObserver()` 的自触发判定原来只看类名是不是以 `ls-` 开头，
    而克隆的类是 `item-ff6fc9 ls-pinned ls-pin-clone`（**应用类名在前**），
    于是被误判成「外部变动」→ 触发 `applyAll()` → `renderPinnedSection()`
    `remove()` 掉所有克隆再重新 `appendChild` → 又触发观察器……实测**每 17ms
    一轮**（探针逐条记录 `lsAdded` 时间戳算出）。用户看到的就是
    「那个框鼠标放上去就会乱跳」「点别的对话，置顶那个也在跳」。
    修法两层：
    - `applyAll()` 入口置 `selfMutating = true`，**在下一个 rAF 才释放**
      （MutationObserver 回调是微任务，同步释放挡不住自己刚造成的变动）。
    - 我们自己造的节点统一打 `data-ls-own`；观察器把「新增/删除的节点自己或
      后代带这个标记」也判为自触发，不再只看类名前缀（`OWN_ATTR` / `markOwn()`）。

    **(2) 克隆行每轮删掉重建，位置会闪。** 即使不再自触发，
    `renderPinnedSection()` 原来仍然无条件重建所有克隆。点一下对话、
    收到一条消息都会走到这里，用户就能看到置顶行「跳」一下。
    现在改成 `syncPinClones()` **能复用就复用**：
    标题集合没变 → 一个节点都不动；顺序变了 → 用 `insertBefore` 挪；
    只有增减置顶时才处理差集。另外 `syncPinActive()` 只同步 `active-ff6fc9`
    类名（克隆是快照，应用不会帮它更新），**不为 active 变化重建节点**。
    验证方式：记下 `window.__cloneRef = clone`，切换对话后核对还是同一个对象。

    **(3) 置顶行的「...」能点开、但菜单跑到屏幕左上角。**
    这是用户说的「不是点不开，是位置不对」。原因链：
    - 克隆清掉了 React 属性 → 事件委托找不到 fiber → 点了没反应。
      所以必须把点击**转发给真身上那个按钮**（`realBtn.click()`）。
    - 但真身整行是 `display:none`，应用量出来的锚点矩形是 0×0（在 0,0），
      于是菜单落在左上角。

    试过、**没用**的两条路（别再走一遍）：
    - 临时覆盖真身（以及它的 `firstElementChild`、祖先链）的
      `getBoundingClientRect`，甚至挂到 `Element.prototype` 上按
      「最近被顶替的祖先」判断 —— 应用量到的仍然不是这些节点，
      菜单照旧在 (8,4)。探针记录显示它量的是真身行里的 `.anchor-_5f384`，
      但覆盖上去也不生效。
    - 用 `flushSync` 强制同步提交。ReactDOM 没挂在 window 上，
      从 fiber 的 root 里也取不到（`syncFlush` 导出会返回 false）。
      代码里留了这条路和退路，但**不能依赖它**。

    最后有效的做法是 `placeMenuAt(menu, cloneBtn)`：**等应用定位完，直接改坐标。**
    菜单是 `position:fixed`（实测 `main.*.css`：`.menu-_5f384{position:fixed}`），
    它的 `left/top` 就是视口坐标，和 `getBoundingClientRect` 同一套坐标系，所以
      `dx = 当前 rect.left - 当前 style.left`，`left = 目标 rect.left + dx`
    —— 这样连「应用哪天改成 transform 定位」也能跟着走。
    位置规则照抄应用观感：水平贴按钮左边并夹在视口内（左右各 8px），
    垂直默认在按钮下方 4px、放不下就翻到上方。
    **必须用 rAF 连续修 4 帧再停**：我们插入的「取消置顶」那一条会让菜单高度
    晚一帧才定下来，只修一次会算错偏移量；修完就交还给应用（滚动/缩放时
    它自己重算，那时菜单已在克隆附近，算出来也是对的）。

    **测试这类交互的两个硬要求（踩过才知道）：**
    - **必须用真指针事件**（CDP `Input.dispatchMouseEvent` 的
      mouseMoved → mousePressed → mouseReleased）。`el.click()` 是合成点击，
      实测**弹不出应用的菜单**（真身、克隆都一样）。只有真指针才会触发
      应用自己的事件链。
    - `:hover` 也一样：`new MouseEvent('mouseover')` 不触发 CSS `:hover`，
      要断言「克隆的 `...` 可见」得在真指针悬停后读 `getBoundingClientRect().width > 0`，
      别只看 `getComputedStyle().display`。
    - 菜单的类名是 **`menu-_5f384`**（不是 `menu-b81146`，那是另一个组件），
      菜单项是 `option-_5f384`。早期测试用错了类名，导致「菜单没弹出」的假失败。

### 上传问题自查

页面 Console 里跑这一行，会打印一段可直接复制的结论：

```js
window.__localstore.uploadLog().report
```

输出形如：

```
bridge v1.1.0 | 提供方=DeepSeek 官方 | 上传地址=https://api.deepseek.com/anthropic/v1/files
| Key=sk-abc…1234 | 尝试=3 | 结果=net::ERR_HTTP2_PROTOCOL_ERROR
```

它同时回答三个最容易搞混的问题：**桥接脚本是不是新的**（版本号）、
**请求打到了哪个地址**（提供方地址归一化是否正确）、**试了几次、最后什么错**。
`uploadLog().entries` 里还有每次尝试的时间、错误类型与上传前的预检快照。

如果结论是 `net::ERR_HTTP2_PROTOCOL_ERROR` 这类**连接层**错误，再跑这一条做逐级定位：

```js
window.__localstore.probeUploads().then(r => r.report)
```

它会按四条最小请求逐级试，全部用 1 字节假文件（不会在你账号里留下东西），
把「预检就断了 / POST 才断 / 与大小有关 / 与 multipart 编码有关」区分开：

| 步骤 | 作用 |
| --- | --- |
| `GET /models` | 基准：无预检的简单请求，验证域名与 Key 通路 |
| `POST /files` 1 字节 multipart | 真实上传路径的最小复现 |
| `POST /files` 64KB multipart | 与**大小**是否相关 |
| `POST /files` 裸二进制 | 与 **multipart 编码**是否相关 |

输出里每步都带耗时：**几毫秒就失败**说明是协议层被拒（连接被掐），
**卡到超时**才是网络不通。这两种原因的排查方向完全不同。

### 已知测试限制

`e2e-api-base.mjs` 中**已移除**「点发送 → 断言服务端收到请求」这一段，
原因已查明且**与本改造无关**：


- 官方应用在**没有配置 API Key** 时会停在「输入 API Key 开始使用」引导界面，
  输入区不会被武装（发送按钮带 `aria-disabled="true"`，并带 `disabled-*` 类），
  点发送不会有任何网络请求。
  已用**未打补丁的官方原始 bundle** 复现同样行为 —— 即这是应用自身的状态门槛。
- 因此该链路的发送动作无法在无人值守的测试里触发。
  该用例改为断言「bundle 补丁实际读取的模型键」，等价于断言请求里的 `model`。

**真实发送链路的覆盖**：`e2e-localstore.mjs` 里的假 SSE 服务端能真实收到
`POST /anthropic/v1/messages`，证明「自定义地址 + API Key + model 字段」
的完整链路是通的；`e2e-features.mjs` 里 `/models` 请求也确实打到了自定义地址
并带上了正确的 Key。

### 升级到新的官方版本时

官方出新版（例如 v0.1.3）后：

1. 用新版本覆盖 `static/`、`index.html`，**不要**覆盖 `localstore-bridge.js` 和 `tools/`
2. 跑 `node tools/apply-patch.mjs`
   - 若报「未找到目标字符串」，说明 bundle 变了，需要按提示更新
     `tools/apply-patch.mjs` 里的匹配串
   - 若报「设置面板 class 变化」，更新 `localstore-bridge.js` 里的
     `SETTINGS_CONTENT_CLASS` 常量
3. 跑 `node tools/verify-patch.mjs` 与 `node tools/e2e-features.mjs` 确认功能正常
